Granular

A single-screen local note editor where pins target characters and palette colors become persistent text highlights.

Approved technical spec

How this works, in plain language

Granular is a browser app. React keeps the screen in sync, TypeScript catches many mistakes before the app runs, and Vite serves it locally. The note is edited in Tiptap: unlike a plain text box, it can keep colored marks attached to text while someone types, pastes, or deletes. The pins point into that same text. One note, its title, and its palette are saved only in this browser—no account or cloud service.

Pieces and data flow

The target pins are the uncertain part: browser coordinates must map accurately to text characters. We’ll test this with spaces, punctuation, wrapped text, and line breaks early.

Components tied to the product

Editor surface · title and rich text

Files: App.tsx, NoteTitle.tsx, NoteEditor.tsx. Implements PRD Editor input and persistence and Highlight range selection. Text edits preserve highlight marks, including newly inserted text inside a highlighted passage.

Targeting and highlight actions

Files: TargetBar.tsx, HighlightActions.tsx, highlight.ts. Implements PRD Highlight range selection and Increment and decrement controls. Each pin targets a character start; the inclusive user range is stored with an exclusive end boundary. Includes one-pin single-character mode, None, held-button repeat, range limits, and a brief character-by-character reveal when applying a color.

Palette, custom color, and help

Files: Palette.tsx, ColorDialog.tsx, color.ts, HelpDialog.tsx. Implements PRD Color pointer bars and Prompt and invalid-state guidance. Starts with one default color; adding uses a cancelable dialog; editing a color updates its existing text highlights.

Local persistence and app styling

Files: useSavedNote.ts, storage.ts, styles.css. Implements PRD Editor input and persistence and States and Boundaries. Reports load/save failures instead of pretending the data was saved.

Data that persists

One versioned record: title, Tiptap JSON document, palette entries (id, label, color), and active color ID. Each highlight mark stores a stable palette ID, not a copied color, so editing a swatch updates its existing highlights. Pins target character starts; the derived range includes the final character using an exclusive document end. Pin positions are temporary and start unset after a refresh.

Build boundaries and checks

Simplifications for this proof of concept
  • One active note, not a library, history, or multi-note workflow.
  • One default yellow swatch; all other colors are user-added.
  • Small in-project HSV controls, rather than an extra picker dependency.
  • No accounts, server, deployment, settings, trash, or sync.
  • Ambatah is listed first with system fallbacks because no font file is present.
Likely failure points and recovery
  • Wrong pin-to-character mapping → show the targeted character and verify spaces, punctuation, wrapped lines, and paragraph boundaries.
  • Highlights detach during editing → use rich-text marks and verify insertion/deletion inside a marked passage.
  • Storage read/write fails or data is invalid → show an explicit warning, keep editing in memory, and do not report a false save.
  • Color dialog is cancelled → discard its draft; do not add or change a sidebar item.

The character-to-screen mapping and compatible package versions are the first build checks. If unusual multi-code-unit characters expose an indexing mismatch, decide whether to extend that mapping before declaring precise targeting complete.
